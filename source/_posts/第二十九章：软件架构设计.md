## 29.1 架构风格

| 风格 | 特点 | 适用场景 |
|------|------|---------|
| 分层架构 | 按职责分层（表示层/业务层/数据层） | 大多数 Web 应用 |
| 微内核架构 | 核心 + 插件 | IDE、规则引擎 |
| 事件驱动架构 | 事件生产者 → 事件总线 → 消费者 | 解耦、异步处理 |
| Serverless | 函数即服务，按需执行 | 低频触发、突发流量 |
| CQRS | 读写分离模型 | 复杂查询、高并发读 |

## 29.2 架构设计方法论

**4+1 视图模型：**
```
逻辑视图：系统的功能需求（类图、对象图）
开发视图：代码组织结构（包图、组件图）
进程视图：并发和同步（序列图、协作图）
物理视图：部署拓扑（部署图）
场景视图：用例驱动，验证其他四个视图
```

**C4 模型：**
```
Context（系统上下文）：系统与外部用户/系统的关系
Container（容器）：系统中的应用、数据库、消息队列
Component（组件）：容器中的模块/组件
Code（代码）：组件的类和接口
```

## 29.3 技术选型原则

```
1. 成熟度：优先选择经过大规模验证的技术
2. 社区活跃度：GitHub Stars、Issue 处理速度、文档质量
3. 团队能力：团队熟悉的技术 > 不熟悉但更优秀的技术
4. 生态兼容：与现有技术栈的兼容性
5. 长期维护：避免使用已停止维护的项目
```

## 29.4 技术债务管理

```
技术债务类型：
├── 故意的债务：为了赶工期的临时方案
├── 无意的债务：设计不足导致的债务
├── 老旧的技术：已过时的技术栈
└── 缺失的文档：缺少必要的文档和注释

管理策略：
1. 识别：代码审查、静态分析、架构适应度函数
2. 评估：影响范围、修复成本、业务影响
3. 排期：纳入迭代计划，分配时间偿还
4. 预防：代码规范、自动化测试、定期重构
```

## 面试精选

### 1. 怎么做架构设计？

1）理解业务需求和非功能需求（性能、可用性、扩展性）。2）选择架构风格（分层、微服务、事件驱动）。3）定义核心模块和接口。4）考虑数据存储方案。5）设计部署架构。6）识别风险和技术选型。7）输出架构文档（C4 模型）。

### 2. 怎么做技术选型？

成熟度 > 社区活跃度 > 团队能力 > 生态兼容 > 长期维护。避免追新，选择经过大规模验证的技术。团队不熟悉的技术需要评估学习成本。

### 3. 怎么管理技术债务？

识别（代码审查+静态分析）→ 评估（影响和成本）→ 排期（纳入迭代）→ 预防（规范+测试+定期重构）。每个迭代分配 20% 时间处理技术债务。
