## 9.1 线程基础

### 9.1.1 进程与线程

- **进程**：操作系统资源分配的基本单位，拥有独立的内存空间
- **线程**：CPU 调度的基本单位，一个进程可以包含多个线程，线程共享进程的内存空间
- **区别**：进程之间内存隔离，线程之间共享堆内存和方法区，但每个线程有自己的程序计数器、虚拟机栈和本地方法栈

### 9.1.2 创建线程的方式

**1. 继承 Thread 类**

```java
public class MyThread extends Thread {
    @Override
    public void run() {
        System.out.println("Thread running: " + getName());
    }
}
new MyThread().start();
```

**2. 实现 Runnable 接口**

```java
new Thread(() -> System.out.println("Runnable running")).start();
```

**3. 实现 Callable + FutureTask**

```java
FutureTask<String> task = new FutureTask<>(() -> {
    Thread.sleep(1000);
    return "task result";
});
new Thread(task).start();
String result = task.get(); // 阻塞获取结果
```

**4. 线程池（推荐方式，后面 9.7 详解）**

```java
ExecutorService pool = Executors.newFixedThreadPool(4);
pool.submit(() -> System.out.println("Pool task"));
```

> **面试考点：** 为什么推荐线程池？因为频繁创建/销毁线程开销大，线程池能复用线程、控制并发数、管理任务队列。

### 9.1.3 线程的生命周期（六种状态）

```
        start()
NEW ──────────→ RUNNABLE ◄──────────────────────┐
                   │                              │
                   │ 获得锁                        │ notify() / notifyAll()
                   ▼                              │
              BLOCKED ──────────→ RUNNABLE ───────┘
                   │
          wait() / join() / LockSupport.park()
                   ▼
              WAITING / TIMED_WAITING
                   │
    notify() / 超时 / LockSupport.unpark()
                   ▼
                 RUNNABLE
                   │
               run() 结束
                   ▼
              TERMINATED
```

| 状态 | 说明 |
|------|------|
| **NEW** | 创建但未调用 `start()` |
| **RUNNABLE** | 就绪或正在运行（JVM 层面不区分） |
| **BLOCKED** | 等待获取 synchronized 锁 |
| **WAITING** | 无限期等待（wait、join、park） |
| **TIMED_WAITING** | 有限期等待（sleep、wait(timeout)） |
| **TERMINATED** | run() 方法执行完毕或异常退出 |

### 9.1.4 线程常用方法对比

| 方法 | 是否释放锁 | 是否抛异常 | 说明 |
|------|-----------|-----------|------|
| `sleep(n)` | 否 | InterruptedException | 暂停执行指定时间（进入 TIMED_WAITING），不释放锁 |
| `wait()` | **是** | InterruptedException | Object 方法，必须在 synchronized 中调用 |
| `join()` | 否 | InterruptedException | 等待目标线程执行完毕 |
| `yield()` | 否 | 否 | 提示调度器让出 CPU，但不保证生效 |
| `interrupt()` | — | — | 设置中断标志位，不会中断线程 |

> **面试考点：sleep 和 wait 的区别？**
> 1. sleep 是 Thread 的静态方法，wait 是 Object 的实例方法
> 2. sleep 不释放锁，wait 释放锁
> 3. sleep 无需在 synchronized 中调用，wait 必须在 synchronized 中调用
> 4. sleep 到时间自动恢复，wait 需要 notify/notifyAll 唤醒

## 9.2 synchronized 与锁升级

### 9.2.1 synchronized 的三种用法

```java
// 1. 修饰实例方法 → 锁的是 this 对象
public synchronized void method() { }

// 2. 修饰静态方法 → 锁的是 Class 对象
public static synchronized void staticMethod() { }

// 3. 修饰代码块 → 锁的是指定对象
synchronized (lockObj) { }
```

### 9.2.2 synchronized 底层原理

- **同步代码块**：编译后在字节码层面生成 `monitorenter` 和 `monitorexit` 指令
- **同步方法**：方法标志位上设置 `ACC_SYNCHRONIZED` 标志
- 本质都是获取对象的 **Monitor（监视器锁）**，每个 Java 对象头中都有一个 Mark Word，用于存储锁信息

### 9.2.3 对象头 Mark Word

在 64 位 JVM 中，Mark Word 占 64 位，存储内容随锁状态变化：

| 锁状态 | Mark Word 内容 | 标志位 |
|--------|---------------|--------|
| 无锁 | HashCode + 分代年龄 | 01 |
| 偏向锁 | 线程 ID + Epoch + 分代年龄 | 01 |
| 轻量级锁 | 指向栈中锁记录的指针 | 00 |
| 重量级锁 | 指向 Monitor 对象的指针 | 10 |
| GC 标记 | 空 | 11 |

### 9.2.4 锁升级过程（JDK 6+ 优化）

```
无锁 → 偏向锁 → 轻量级锁 → 重量级锁
```

**偏向锁（Biased Locking）**
- 场景：只有一个线程反复进入同步块
- 原理：第一次获取锁时，将线程 ID 记录到 Mark Word 中，后续同一线程进入时只需比较线程 ID，无需 CAS 操作
- 开销：几乎零开销

**轻量级锁（Lightweight Locking）**
- 场景：多个线程交替进入同步块（无实际竞争）
- 原理：JVM 在当前线程栈帧中创建锁记录（Lock Record），将 Mark Word 复制到锁记录中，通过 CAS 尝试将 Mark Word 指向锁记录
- 失败则自旋等待

**重量级锁（Heavyweight Locking）**
- 场景：多个线程真正同时竞争锁
- 原理：未获取锁的线程会被阻塞（挂起），通过操作系统的 Mutex Lock 实现，涉及用户态→内核态切换，开销较大

> **面试考点：synchronized 锁升级能降级吗？**
> 重量级锁在 GC 时可以降级，但偏向锁和轻量级锁不能主动降级。JDK 15 开始默认禁用偏向锁（JEP 374），因为现代应用中偏向锁的收益很小，反而增加了撤销开销。

## 9.3 volatile 与内存可见性

### 9.3.1 volatile 的两个作用

**1. 保证可见性**

```java
volatile boolean flag = false;

// 线程 A
flag = true;  // 写入后立即刷新到主内存

// 线程 B
while (!flag) { }  // 读取时直接从主内存读取，不会用缓存的旧值
```

**2. 禁止指令重排序**

经典案例——双重检查锁定单例的正确写法：

```java
public class Singleton {
    private static volatile Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {                // 第一次检查
            synchronized (Singleton.class) {
                if (instance == null) {         // 第二次检查
                    instance = new Singleton(); // 需要 volatile 防止重排序
                }
            }
        }
        return instance;
    }
}
```

`new Singleton()` 实际包含三步：
1. 分配内存空间
2. 初始化对象
3. 将引用指向分配的内存

如果没有 volatile，步骤 2 和 3 可能重排序，导致其他线程拿到未初始化完成的对象。

### 9.3.2 volatile 不保证原子性

```java
volatile int count = 0;
// count++ 不是原子操作！包含 读取→加1→写入 三步
// 多线程下仍然会出现数据不一致，需要用 AtomicInteger 或 synchronized
```

### 9.3.3 volatile vs synchronized

| 特性 | volatile | synchronized |
|------|----------|-------------|
| 原子性 | 不保证 | 保证 |
| 可见性 | 保证 | 保证 |
| 有序性 | 保证（禁止重排序） | 保证 |
| 阻塞 | 不会 | 会 |
| 适用场景 | 一写多读、状态标志 | 复合操作、临界区保护 |

## 9.4 JMM（Java 内存模型）与 happens-before

### 9.4.1 JMM 抽象结构

```
┌──────────┐   ┌──────────┐   ┌──────────┐
│  线程 A   │   │  线程 B   │   │  线程 C   │
│ 工作内存  │   │ 工作内存  │   │ 工作内存  │
│ (本地缓存)│   │ (本地缓存)│   │ (本地缓存)│
└────┬─────┘   └────┬─────┘   └────┬─────┘
     │              │              │
     └──────────────┼──────────────┘
                    ▼
              ┌──────────┐
              │ 主内存    │
              │ (共享变量)│
              └──────────┘
```

JMM 定义了线程之间共享变量的可见性规则：
- 所有变量存储在主内存
- 每个线程有自己的工作内存（CPU 缓存的抽象）
- 线程对变量的操作必须在工作内存中进行，不能直接读写主内存
- 线程间变量传递必须经过主内存

### 9.4.2 happens-before 规则

如果操作 A happens-before 操作 B，那么 A 的结果对 B 可见：

1. **程序顺序规则**：同一线程中，前面的操作 happens-before 后面的操作
2. **volatile 变量规则**：volatile 写 happens-before 后续的 volatile 读
3. **监视器锁规则**：unlock happens-before 后续的 lock
4. **线程启动规则**：`thread.start()` happens-before 该线程的每个操作
5. **线程终止规则**：线程中所有操作 happens-before `thread.join()` 返回
6. **传递性规则**：如果 A hb B，B hb C，则 A hb C
7. **线程中断规则**：`interrupt()` happens-before 检测到中断
8. **对象终结规则**：构造函数结束 happens-before `finalize()` 开始

> **面试考点：JMM 解决了什么问题？**
> JMM 屏蔽了不同硬件和操作系统的内存访问差异，为 Java 程序员提供了一套统一的并发内存可见性保证。核心问题是：CPU 缓存导致的可见性问题、指令重排导致的有序性问题、以及非原子操作导致的原子性问题。

## 9.5 Lock 体系

### 9.5.1 ReentrantLock

```java
private final ReentrantLock lock = new ReentrantLock();

public void safeMethod() {
    lock.lock();
    try {
        // 临界区代码
    } finally {
        lock.unlock(); // 必须在 finally 中释放
    }
}
```

**ReentrantLock vs synchronized**

| 特性 | synchronized | ReentrantLock |
|------|-------------|---------------|
| 锁获取方式 | 自动获取释放 | 手动 lock/unlock |
| 可中断 | 不可 | `lockInterruptibly()` |
| 超时机制 | 无 | `tryLock(timeout)` |
| 公平锁 | 非公平 | 可选公平/非公平 |
| 条件变量 | 1 个（wait/notify） | 多个 Condition |
| 底层实现 | JVM 指令 | AQS 框架 |

### 9.5.2 ReadWriteLock

```java
ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();
rwLock.readLock().lock();   // 读锁（共享锁）
rwLock.writeLock().lock();  // 写锁（排他锁）
```

- 读读共享、读写互斥、写写互斥
- 适用于读多写少的场景

### 9.5.3 StampedLock（JDK 8+）

```java
StampedLock sl = new StampedLock();

// 乐观读（不加锁，通过版本号判断是否有写入）
long stamp = sl.tryOptimisticRead();
// ... 读取数据 ...
if (!sl.validate(stamp)) {
    // 有写入发生，升级为悲观读锁
    stamp = sl.readLock();
    try { /* 重新读取 */ } finally { sl.unlockRead(stamp); }
}
```

- 支持乐观读（不加锁，适合读远多于写的场景）
- 不支持重入，不能替代 ReadWriteLock 的所有场景

## 9.6 AQS（AbstractQueuedSynchronizer）原理

### 9.6.1 AQS 是什么

AQS 是 Java 并发包的基石，ReentrantLock、Semaphore、CountDownLatch、ReadWriteLock 等都基于 AQS 实现。

**核心结构：**

```
┌─────────────────────────────────────────┐
│              AQS（共享资源）              │
│                                         │
│  state (volatile int)                   │
│  ├─ ReentrantLock: 重入次数              │
│  ├─ Semaphore: 可用许可数                │
│  ├─ CountDownLatch: 计数值               │
│  └─ ReadWriteLock: 高16位=读锁计数       │
│                  低16位=写锁重入次数      │
│                                         │
│  CLH 双向队列 (等待队列)                  │
│  ┌───┐  ┌───┐  ┌───┐  ┌───┐           │
│  │ T1│◄─│ T2│◄─│ T3│◄─│ T4│           │
│  └───┘  └───┘  └───┘  └───┘           │
│   head                            tail  │
└─────────────────────────────────────────┘
```

### 9.6.2 独占锁获取流程（以 ReentrantLock 为例）

```
lock.lock()
    │
    ▼
tryAcquire(1)  ← 尝试 CAS 修改 state
    │
    ├─ 成功 → 获得锁，返回
    │
    └─ 失败 → addWaiter(Node.EXCLUSIVE)  ← 将当前线程封装为 Node 加入队尾
                │
                ▼
         acquireQueued()  ← 自旋 + park 阻塞
                │
                ├─ 前驱是 head 且 tryAcquire 成功 → 出队，获得锁
                │
                └─ 否则 → LockSupport.park() 挂起
```

### 9.6.3 AQS 模板方法模式

子类通过重写以下方法来实现不同的同步器：

```java
tryAcquire(int arg)       // 独占方式获取
tryRelease(int arg)       // 独占方式释放
tryAcquireShared(int arg) // 共享方式获取
tryReleaseShared(int arg) // 共享方式释放
isHeldExclusively()       // 是否被当前线程独占
```

> **面试考点：AQS 为什么要用 CLH 队列而不是自旋？**
> 纯自旋会让所有等待线程都消耗 CPU，浪费资源。AQS 用 CLH 变体队列：只有队首的线程（head 的后继节点）才自旋尝试获取锁，其余线程通过 `LockSupport.park()` 挂起，减少 CPU 空转。唤醒时只 unpark 队首线程，避免惊群效应。

## 9.7 线程池

### 9.7.1 为什么用线程池

- **降低资源消耗**：复用线程，减少创建/销毁开销
- **提高响应速度**：任务到达时无需等待线程创建
- **提高可管理性**：统一管理、调优、监控
- **防止资源耗尽**：控制最大并发数

### 9.7.2 ThreadPoolExecutor 七大参数

```java
public ThreadPoolExecutor(
    int corePoolSize,       // 核心线程数（即使空闲也不会回收，除非 allowCoreThreadTimeOut）
    int maximumPoolSize,    // 最大线程数
    long keepAliveTime,     // 非核心线程的空闲存活时间
    TimeUnit unit,          // 时间单位
    BlockingQueue<Runnable> workQueue,  // 任务队列
    ThreadFactory threadFactory,         // 线程工厂（可自定义线程名等）
    RejectedExecutionHandler handler     // 拒绝策略
)
```

### 9.7.3 任务执行流程

```
提交任务
    │
    ▼
当前线程数 < corePoolSize ？
    ├─ 是 → 创建核心线程执行任务
    │
    └─ 否 → 任务队列未满？
              ├─ 是 → 任务入队等待
              │
              └─ 否 → 当前线程数 < maximumPoolSize？
                        ├─ 是 → 创建非核心线程执行任务
                        │
                        └─ 否 → 执行拒绝策略
```

**面试要点：为什么不先入队再创建线程？**
当核心线程满时，新任务先放入队列等待（而非立即创建新线程），这是设计有意为之——优先让核心线程复用，只有队列满了才会创建非核心线程，减少了线程创建的开销。

### 9.7.4 常用阻塞队列

| 队列 | 特点 | 适用场景 |
|------|------|---------|
| `LinkedBlockingQueue` | 链表实现，默认无界 | 不限制任务数量（注意 OOM） |
| `ArrayBlockingQueue` | 数组实现，有界 | 限制任务数量 |
| `SynchronousQueue` | 不存储元素，直接传递 | 要求高吞吐，任务不堆积 |
| `PriorityBlockingQueue` | 优先级排序 | 任务有优先级 |
| `DelayedWorkQueue` | 延迟队列 | ScheduledThreadPoolExecutor |

### 9.7.5 四种拒绝策略

| 策略 | 行为 |
|------|------|
| `AbortPolicy`（默认） | 抛出 RejectedExecutionException |
| `CallerRunsPolicy` | 由提交任务的线程自己执行 |
| `DiscardPolicy` | 直接丢弃任务，不抛异常 |
| `DiscardOldestPolicy` | 丢弃队列中最老的任务，重新提交 |

### 9.7.6 Executors 工厂方法（了解即可，生产不推荐）

| 方法 | 核心/最大线程 | 队列 | 风险 |
|------|-------------|------|------|
| `newFixedThreadPool(n)` | n / n | LinkedBlockingQueue（无界） | OOM |
| `newSingleThreadExecutor()` | 1 / 1 | LinkedBlockingQueue（无界） | OOM |
| `newCachedThreadPool()` | 0 / Integer.MAX | SynchronousQueue | 创建过多线程 |
| `newScheduledThreadPool(n)` | n / MAX | DelayedWorkQueue | — |

> **面试考点：为什么阿里规约禁止使用 Executors 创建线程池？**
> 因为 `FixedThreadPool` 和 `SingleThreadExecutor` 使用无界 `LinkedBlockingQueue`，任务可以无限堆积导致 OOM；`CachedThreadPool` 最大线程数为 `Integer.MAX_VALUE`，可能导致创建大量线程导致 OOM。应该手动 `new ThreadPoolExecutor()` 并显式指定有界队列和合适的拒绝策略。

### 9.7.7 线程池参数设定经验

- **CPU 密集型任务**：核心线程数 = CPU 核心数 + 1（减少上下文切换）
- **IO 密集型任务**：核心线程数 = CPU 核心数 × 2（或根据 IO 等待比例计算）
- **通用公式**：线程数 = CPU 核心数 × (1 + IO 等待时间 / CPU 计算时间)
- 生产环境建议通过压测确定最优值

### 9.7.8 线程池监控

```java
// 关键监控指标
pool.getActiveCount();      // 活跃线程数
pool.getPoolSize();         // 当前线程数
pool.getCorePoolSize();     // 核心线程数
pool.getMaximumPoolSize();  // 最大线程数
pool.getQueue().size();     // 队列中等待的任务数
pool.getCompletedTaskCount(); // 已完成任务数
pool.getTaskCount();        // 总任务数（已完成 + 排队 + 执行中）
```

## 9.8 并发集合

### 9.8.1 ConcurrentHashMap（JDK 8+）

**结构变化（JDK 7 → JDK 8）：**
- JDK 7：Segment 分段锁（默认 16 个 Segment，最多 16 个线程并发写）
- JDK 8：Node 数组 + 链表/红黑树，CAS + synchronized（锁粒度细化到桶级别）

**核心源码流程（put 操作）：**

```java
final V putVal(K key, V value) {
    // 1. 计算 hash，定位到桶
    // 2. 如果桶为空 → CAS 写入（无锁）
    // 3. 如果桶正在扩容 → 协助扩容（helpTransfer）
    // 4. 如果桶不为空 → synchronized 锁住头节点
    //    4.1 链表 → 遍历写入/替换
    //    4.2 红黑树 → 树节点操作
    //    4.3 链表长度 ≥ 8 → 转红黑树（数组长度 ≥ 64 时）
    // 5. 检查是否需要扩容
}
```

**关键设计：**

```java
// JDK 8 中用 Node 的 hash 字段的高两位表示状态
static final int MOVED = -1;   // 正在扩容
static final int TREEBIN = -2; // 红黑树根节点
static final int RESERVED = -3; // 临时保留

// sizeCtl 变量的多重含义
-1：正在初始化
-N：有 N-1 个线程在扩容
正数：下次扩容的阈值（默认 = 容量 × 0.75）
```

**为什么 ConcurrentHashMap 的 key 和 value 不能为 null？**
- 因为在并发环境下，如果 `get()` 返回 null，无法区分是 key 不存在还是 value 本身就是 null
- HashMap 可以用 `containsKey()` 区分，但 ConcurrentHashMap 的 `get()` 和 `containsKey()` 之间可能有并发修改

### 9.8.2 CopyOnWriteArrayList

```java
// 写时复制：写操作时复制整个数组
public boolean add(E e) {
    synchronized (lock) {
        Object[] oldArray = array;
        Object[] newArray = Arrays.copyOf(oldArray, oldArray.length + 1);
        newArray[oldArray.length] = e;
        array = newArray;  // 替换引用（volatile）
        return true;
    }
}

// 读操作无锁
public E get(int index) {
    return array[index];  // 直接读取，无需加锁
}
```

- 适用场景：读多写少（如配置列表、监听器列表）
- 缺点：写操作需要复制整个数组，内存开销大；数据有一定延迟（最终一致性）

## 9.9 原子类与 CAS

### 9.9.1 CAS 原理

CAS（Compare And Swap）是一种无锁并发原语，包含三个操作数：

```
CAS(内存地址V, 期望值A, 新值B)
→ 如果 V 的当前值 == A，则将 V 更新为 B，返回 true
→ 否则什么都不做，返回 false
```

底层通过 CPU 的原子指令 `cmpxchg` 实现（在 x86 架构上）。

### 9.9.2 Unsafe 类

```java
// AtomicInteger 的核心实现
public final int incrementAndGet() {
    return U.getAndAddInt(this, VALUE, 1) + 1;
    // 底层循环 CAS
}
```

`sun.misc.Unsafe` 是 JDK 内部类，提供直接操作内存的能力：
- `compareAndSwapInt` / `compareAndSwapLong` / `compareAndSwapObject`
- `getIntVolatile` / `putIntVolatile`（volatile 读写）

### 9.9.3 原子类分类

| 类型 | 类 |
|------|-----|
| 基本类型 | AtomicInteger、AtomicLong、AtomicBoolean |
| 数组 | AtomicIntegerArray、AtomicLongArray |
| 引用 | AtomicReference、AtomicStampedReference、AtomicMarkableReference |
| 字段更新 | AtomicIntegerFieldUpdater、AtomicReferenceFieldUpdater |

### 9.9.4 ABA 问题与解决

**问题**：线程 1 读取值 A，线程 2 将 A→B→A，线程 1 CAS 时发现仍是 A，但实际已被修改过。

**解决**：

```java
// AtomicStampedReference — 版本号
AtomicStampedReference<Integer> ref = new AtomicStampedReference<>(1, 0);
int stamp = ref.getStamp(); // 获取版本号
ref.compareAndSet(1, 2, stamp, stamp + 1);

// AtomicMarkableReference — 布尔标记
AtomicMarkableReference<Integer> ref = new AtomicMarkableReference<>(1, false);
```

### 9.9.5 CAS 的问题

1. **ABA 问题**：用 AtomicStampedReference 解决
2. **自旋开销**：竞争激烈时 CAS 长时间失败导致 CPU 空转
3. **只能保证一个变量的原子操作**：多个变量需要用锁或 AtomicReference 封装

## 9.10 CountDownLatch、CyclicBarrier、Semaphore

### 9.10.1 CountDownLatch（倒计时器，一次性）

```java
// 等待 N 个任务完成后继续
CountDownLatch latch = new CountDownLatch(3);

for (int i = 0; i < 3; i++) {
    new Thread(() -> {
        try {
            doSomething();
        } finally {
            latch.countDown(); // 计数减 1
        }
    }).start();
}

latch.await(); // 阻塞直到计数归零
System.out.println("所有任务完成");
```

- 一次性使用，计数不能重置
- 典型场景：主线程等待多个子任务完成、并行计算汇总

### 9.10.2 CyclicBarrier（循环栅栏，可复用）

```java
// N 个线程互相等待到齐后一起继续
CyclicBarrier barrier = new CyclicBarrier(3, () -> {
    System.out.println("所有线程已就位，开始执行");
});

for (int i = 0; i < 3; i++) {
    new Thread(() -> {
        try {
            System.out.println("准备就绪");
            barrier.await(); // 等待其他线程
            System.out.println("开始执行");
        } catch (Exception e) { }
    }).start();
}
```

- 可循环使用（所有线程到达屏障后自动重置，可用于下一轮同步）
- 典型场景：多线程分阶段计算、并行任务同步

### 9.10.3 Semaphore（信号量）

```java
// 控制同时访问的线程数
Semaphore semaphore = new Semaphore(3); // 最多 3 个并发

for (int i = 0; i < 10; i++) {
    new Thread(() -> {
        try {
            semaphore.acquire();  // 获取许可（阻塞）
            System.out.println("获得许可，执行任务");
            doSomething();
        } finally {
            semaphore.release();  // 释放许可
        }
    }).start();
}
```

- 典型场景：限流、连接池管理、资源池

### 9.10.4 三者对比

| 特性 | CountDownLatch | CyclicBarrier | Semaphore |
|------|---------------|---------------|-----------|
| 作用 | 等待 N 个事件完成 | N 个线程互相等待 | 控制并发数 |
| 可重用 | 否 | 是 | 是 |
| 计数方向 | 递减到 0 | 递增到 N | acquire/release |
| 触发条件 | 计数归零 | 所有线程到达屏障点 | 有许可可用 |
| 基于 | AQS（共享模式） | ReentrantLock + Condition | AQS（共享模式） |

## 9.11 CompletableFuture 异步编程

### 9.11.1 基本用法

```java
// 创建异步任务
CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> {
    return queryFromDB();
});

// 链式处理
future.thenApply(result -> result.toUpperCase())      // 同步转换
      .thenApplyAsync(result -> result + "!")         // 异步转换
      .thenAccept(result -> System.out.println(result)); // 消费结果
```

### 9.11.2 常用 API

```java
// 组合两个异步任务
CompletableFuture<String> f1 = CompletableFuture.supplyAsync(() -> "Hello");
CompletableFuture<String> f2 = CompletableFuture.supplyAsync(() -> "World");

// 两个都完成后合并
f1.thenCombine(f2, (a, b) -> a + " " + b);

// 两个都完成
CompletableFuture.allOf(f1, f2).join();

// 任意一个完成
CompletableFuture.anyOf(f1, f2).join();
```

### 9.11.3 异常处理

```java
CompletableFuture.supplyAsync(() -> {
    if (error) throw new RuntimeException("fail");
    return "ok";
}).exceptionally(ex -> {
    return "fallback";  // 异常时的降级值
}).thenAccept(System.out::println);

// handle 同时处理正常和异常结果
future.handle((result, ex) -> {
    if (ex != null) return "error: " + ex.getMessage();
    return result;
});
```

> **面试考点：CompletableFuture 和 Future 的区别？**
> 1. Future.get() 会阻塞，CompletableFuture 支持回调，无需阻塞
> 2. Future 不能链式组合，CompletableFuture 支持链式调用、组合、异常处理
> 3. CompletableFuture 支持异步回调（thenApplyAsync 等）
> 4. CompletableFuture 支持 allOf/anyOf 多任务编排

## 9.12 ForkJoin 框架与工作窃取

### 9.12.1 核心思想

```
大任务
  ├── 子任务 1
  │     ├── 子任务 1.1
  │     └── 子任务 1.2
  └── 子任务 2
        ├── 子任务 2.1
        └── 子任务 2.2
```

- **分治**：大任务递归拆分为小任务
- **工作窃取**：空闲线程从其他线程的双端队列尾部"偷"任务执行，提高 CPU 利用率

### 9.12.2 使用方式

```java
public class SumTask extends RecursiveTask<Long> {
    private final long[] array;
    private final int start, end;
    private static final int THRESHOLD = 10000;

    @Override
    protected Long compute() {
        if (end - start <= THRESHOLD) {
            // 小任务直接计算
            long sum = 0;
            for (int i = start; i < end; i++) sum += array[i];
            return sum;
        }
        // 拆分任务
        int mid = (start + end) / 2;
        SumTask left = new SumTask(array, start, mid);
        SumTask right = new SumTask(array, mid, end);
        left.fork();             // 异步执行左任务
        long rightResult = right.compute(); // 当前线程执行右任务
        long leftResult = left.join();      // 等待左任务结果
        return leftResult + rightResult;
    }
}

ForkJoinPool pool = new ForkJoinPool();
long result = pool.invoke(new SumTask(array, 0, array.length));
```

> **面试考点：ForkJoinPool 和普通线程池的区别？**
> 1. ForkJoinPool 使用工作窃取算法，空闲线程可以偷取其他线程队列中的任务
> 2. 普通线程池所有线程从同一个队列取任务，存在竞争
> 3. ForkJoinPool 适合递归分治型任务，普通线程池适合独立任务
> 4. `parallelStream()` 底层使用 `ForkJoinPool.commonPool()`

## 9.13 ThreadLocal 原理与内存泄漏

### 9.13.1 核心原理

每个 Thread 内部持有一个 `ThreadLocalMap`，key 是 ThreadLocal 对象（弱引用），value 是存储的值。

```
Thread
 └── ThreadLocalMap (自定义 HashMap)
      ├── Entry[0]: key=ThreadLocal@A (weak)  → value="data1"
      ├── Entry[1]: key=ThreadLocal@B (weak)  → value="data2"
      └── Entry[2]: null (key 已被 GC)        → value="data3" ← 内存泄漏！
```

### 9.13.2 内存泄漏原因

```java
// Entry 的 key 是弱引用
static class Entry extends WeakReference<ThreadLocal<?>> {
    Object value; // value 是强引用！
}
```

当 ThreadLocal 对象被 GC 回收后（弱引用），Entry 的 key 变为 null，但 value 仍然是强引用，不会被回收。如果线程（尤其是线程池中的线程）一直存活，value 就永远不会释放。

**解决方案**：用完后必须调用 `threadLocal.remove()`

### 9.13.3 典型应用场景

- 数据库连接（每个线程独立的 Connection）
- 用户 Session 信息传递
- 日期格式化（SimpleDateFormat 非线程安全，每个线程一个实例）
- 链路追踪（TraceId 传递）

## 9.14 死锁分析与排查

### 9.14.1 死锁的四个必要条件

1. **互斥**：资源同一时刻只能被一个线程持有
2. **持有并等待**：线程持有资源的同时等待其他资源
3. **不可剥夺**：已持有的资源不能被强制释放
4. **循环等待**：线程之间形成环形等待链

### 9.14.2 死锁示例

```java
Object lockA = new Object();
Object lockB = new Object();

// 线程 1
synchronized (lockA) {
    Thread.sleep(100);
    synchronized (lockB) { }  // 等待 lockB
}

// 线程 2
synchronized (lockB) {
    Thread.sleep(100);
    synchronized (lockA) { }  // 等待 lockA → 循环等待！
}
```

### 9.14.3 排查方法

**1. jstack 命令**

```bash
# 找到 Java 进程 PID
jps -l

# 输出线程栈
jstack <PID>

# 输出中会自动检测死锁：
# Found one Java-level deadlock:
# "Thread-1":
#   waiting to lock monitor 0x... (object 0x..., a java.lang.Object),
#   which is held by "Thread-0"
```

**2. jconsole / VisualVM**
- 连接目标进程 → 线程 tab → 检测死锁按钮

**3. 代码层面预防**
- 固定加锁顺序（所有线程按相同顺序获取锁）
- 使用 `tryLock` 设置超时
- 尽量减少锁的嵌套

> **面试考点：如何避免死锁？**
> 1. 固定锁获取顺序（如按对象 hashCode 排序）
> 2. 设置锁超时（tryLock）
> 3. 减少锁的粒度和持有时间
> 4. 使用并发工具替代手动加锁（如 ConcurrentHashMap）

## 面试精选

### 1. synchronized 和 ReentrantLock 的区别？

synchronized 是 JVM 层面的关键字，自动加锁释放锁，不可中断、非公平；ReentrantLock 是 API 层面的类，需手动加锁释放（try-finally），支持可中断、超时、公平锁、多 Condition。JDK 6 以后 synchronized 做了大量优化（偏向锁、轻量级锁），两者性能差距已很小。优先用 synchronized，需要高级特性时用 ReentrantLock。

### 2. volatile 能保证线程安全吗？

不能。volatile 只保证可见性和有序性，不保证原子性。例如 `volatile int count; count++` 在多线程下仍不安全，因为 `count++` 是读-改-写三步操作。线程安全需要原子性保证，应使用 `AtomicInteger` 或 `synchronized`。

### 3. 线程池的执行流程？

提交任务 → 核心线程未满则创建核心线程执行 → 核心线程满则放入任务队列 → 队列满则创建非核心线程执行 → 线程数达到最大值则执行拒绝策略。

### 4. 为什么不建议用 Executors 创建线程池？

FixedThreadPool 和 SingleThreadExecutor 使用无界 LinkedBlockingQueue，任务可以无限堆积导致 OOM；CachedThreadPool 最大线程数为 Integer.MAX_VALUE，高并发下可能创建大量线程导致 OOM。应手动 new ThreadPoolExecutor 并指定有界队列和拒绝策略。

### 5. CAS 的 ABA 问题怎么解决？

使用 AtomicStampedReference，每次修改时版本号 +1，CAS 时不仅比较值还比较版本号。或者用 AtomicMarkableReference 加布尔标记。

### 6. ThreadLocal 内存泄漏的原因和解决？

ThreadLocalMap 的 Entry 的 key 是弱引用，GC 后变 null，但 value 是强引用不会释放。线程池场景下线程长期存活导致 value 泄漏。解决方案：使用后务必调用 `remove()` 方法。

### 7. CountDownLatch 和 CyclicBarrier 的区别？

CountDownLatch 是一次性计数器，一个线程等待其他 N 个线程完成；CyclicBarrier 是可复用的屏障，N 个线程互相等待到齐后一起执行。CountDownLatch 计数递减，CyclicBarrier 计数递增。CountDownLatch 不能重置，CyclicBarrier 可以 reset。

### 8. ConcurrentHashMap JDK 7 和 JDK 8 的区别？

JDK 7 使用 Segment 分段锁（默认 16 个），并发度受限于 Segment 数量。JDK 8 放弃分段锁，使用 Node 数组 + 链表/红黑树，通过 CAS + synchronized（锁粒度到桶级别）实现更高的并发度，且引入红黑树优化 hash 冲突。

### 9. 如何排查线上死锁？

jstack PID 命令可以自动检测死锁并输出涉及的线程和锁信息。jconsole/VisualVM 连接后点击"检测死锁"也可发现。代码层面预防：固定加锁顺序、tryLock 设置超时、减少锁嵌套。

### 10. CompletableFuture 和 Future 的区别？

Future.get() 会阻塞，CompletableFuture 支持回调无阻塞；Future 不能链式组合，CompletableFuture 支持 thenApply/thenCompose/thenCombine 等链式调用和 allOf/anyOf 多任务编排；CompletableFuture 支持自定义线程池。
