## 17.1 单体 → SOA → 微服务演进

```
单体架构：
所有功能模块打包在一个应用中，共享一个数据库
优点：开发简单、部署方便
缺点：耦合严重、扩展困难、技术栈单一

SOA（面向服务架构）：
将功能拆分为独立的服务，通过 ESB（企业服务总线）通信
优点：服务解耦、可复用
缺点：ESB 重量级、治理复杂

微服务架构：
每个服务独立部署、独立数据库、轻量级通信（HTTP/RPC）
优点：独立部署、技术栈自由、弹性扩展
缺点：分布式复杂性、运维成本高
```

| 特性 | 单体 | SOA | 微服务 |
|------|------|-----|--------|
| 粒度 | 整个应用 | 粗粒度服务 | 细粒度服务 |
| 通信 | 方法调用 | ESB | HTTP/RPC |
| 数据库 | 共享 | 共享/独立 | 独立 |
| 部署 | 整体部署 | 整体/独立 | 独立部署 |
| 技术栈 | 统一 | 统一 | 自由选择 |

## 17.2 微服务设计原则与拆分策略

### 17.2.1 拆分原则

**单一职责原则**：每个服务只负责一个业务领域
**高内聚低耦合**：服务内部紧密关联，服务之间松散依赖
**领域驱动拆分**：按限界上下文（Bounded Context）拆分

### 17.2.2 拆分策略

```
垂直拆分：按业务领域拆分
├── 用户服务（用户管理、认证授权）
├── 订单服务（订单创建、支付、退款）
├── 商品服务（商品管理、库存）
└── 通知服务（短信、邮件、推送）

水平拆分：按通用能力拆分
├── 网关服务（路由、限流、鉴权）
├── 配置中心（动态配置管理）
└── 注册中心（服务注册与发现）
```

## 17.4 CAP 理论与 BASE 理论

### 17.4.1 CAP 定理

分布式系统最多同时满足以下三项中的两项：

- **C（Consistency）一致性**：所有节点看到相同的数据
- **A（Availability）可用性**：每个请求都能得到响应
- **P（Partition Tolerance）分区容错**：网络分区时系统仍能运行

```
CA（放弃分区容错）：单机数据库
CP（放弃可用性）：ZooKeeper、HBase、Redis Cluster
AP（放弃一致性）：Eureka、CouchDB、DynamoDB
```

> **分布式系统必须保证 P（网络分区不可避免），所以只能在 C 和 A 之间选择。**

### 17.4.2 BASE 理论

BASE 是 CAP 的折中方案：

- **BA（Basically Available）基本可用**：系统在故障时保证核心功能可用
- **S（Soft State）软状态**：允许系统存在中间状态（如数据同步中）
- **E（Eventually Consistent）最终一致性**：经过一段时间后，所有节点数据一致

> **大多数互联网系统选择 AP + BASE：放弃强一致性，保证可用性，通过补偿机制实现最终一致性。**

## 17.5 DDD 与微服务结合实践

```
DDD 指导微服务拆分：
1. 战略设计：识别限界上下文 → 每个上下文对应一个微服务
2. 战术设计：每个微服务内部使用实体、值对象、聚合根、领域事件

示例（电商系统）：
├── 用户上下文 → 用户服务
│   └── 聚合根：User（包含 Address 值对象）
├── 商品上下文 → 商品服务
│   └── 聚合根：Product（包含 SKU）
├── 订单上下文 → 订单服务
│   └── 聚合根：Order（包含 OrderItem）
├── 支付上下文 → 支付服务
│   └── 聚合根：Payment
└── 库存上下文 → 库存服务
    └── 聚合根：Inventory
```

## 面试精选

### 1. 单体、SOA、微服务的区别？

单体所有功能打包在一起，共享数据库。SOA 通过 ESB 集成粗粒度服务。微服务每个服务独立部署、独立数据库、轻量级通信。微服务是 SOA 的进一步细化，强调去中心化、独立部署、技术栈自由。

### 2. CAP 理论是什么？为什么只能选两个？

分布式系统最多满足一致性、可用性、分区容错中的两项。网络分区不可避免（必须保证 P），所以只能在 C（一致性）和 A（可用性）之间选择。CP 系统（如 ZooKeeper）保证一致性牺牲可用性，AP 系统（如 Eureka）保证可用性牺牲强一致性。

### 3. BASE 理论是什么？

BASE 是 CAP 的折中：基本可用（核心功能可用）、软状态（允许中间状态）、最终一致性（一段时间后数据一致）。大多数互联网系统选择 AP + BASE，通过补偿机制实现最终一致性。

### 4. 微服务怎么拆分？

按业务领域垂直拆分（用户、订单、商品），遵循单一职责和高内聚低耦合。推荐用 DDD 限界上下文指导拆分：每个限界上下文对应一个微服务，内部使用聚合根管理数据一致性。

### 5. 微服务架构有什么挑战？

服务间通信、分布式事务、服务治理（注册发现、负载均衡、熔断降级）、配置管理、链路追踪、部署运维复杂度。需要引入完整的服务治理框架（Spring Cloud）和 DevOps 工具链。
