## 21.1 分布式 ID 生成

| 方案 | 优点 | 缺点 |
|------|------|------|
| UUID | 简单、无依赖 | 无序、太长、不适合做主键 |
| 数据库自增 | 简单、有序 | 单点瓶颈、分库后不唯一 |
| 雪花算法 | 有序、高性能、去中心化 | 时钟回拨问题 |
| Leaf（美团） | 号段模式 + 雪花模式 | 需要部署服务 |

**雪花算法（Snowflake）结构（64 位）：**
```
0 | 41 位时间戳 | 10 位机器ID | 12 位序列号
符号位 | 毫秒级时间戳    | 支持1024节点 | 每毫秒4096个ID
```

## 21.2 分布式锁

| 方案 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| Redis | SETNX + 过期时间 | 性能高 | 主从切换可能丢锁 |
| ZooKeeper | 临时顺序节点 | 强一致 | 性能较低 |
| 数据库 | 唯一索引 | 简单 | 性能最差 |

```java
// Redis 分布式锁（Redisson 推荐）
RLock lock = redisson.getLock("order:lock:" + orderId);
try {
    if (lock.tryLock(5, 30, TimeUnit.SECONDS)) {
        // 业务逻辑
    }
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

## 21.3 分布式会话

```
方案1：Session 复制（Tomcat 集群同步，性能差）
方案2：Session 粘滞（负载均衡固定到同一节点，不支持故障转移）
方案3：Session 集中存储（Redis 存储 Session，推荐）
方案4：JWT（无状态 Token，不依赖服务端 Session）
```

**JWT 结构：**
```
Header.Payload.Signature
Base64({alg: "HS256", typ: "JWT"}).Base64({sub: "1234", name: "Tom", exp: 1700000000}).HMACSHA256(header+payload, secret)
```

## 21.4 分布式缓存设计

```
多级缓存架构：
客户端 → L1 本地缓存（Caffeine）→ L2 分布式缓存（Redis）→ 数据库

缓存一致性策略：
- Cache Aside（旁路缓存）：读缓存 → 未命中查库 → 写缓存
  写操作：先更新数据库 → 再删除缓存
- Read/Write Through：缓存层统一代理读写
- Write Behind：异步写入数据库（最终一致性）
```

## 面试精选

### 1. 雪花算法的原理？时钟回拨怎么处理？

64位ID：1位符号+41位时间戳+10位机器ID+12位序列号。时钟回拨处理：等待时钟追上、使用扩展位记录回拨次数、或切换到备用机器ID。

### 2. Redis 分布式锁的原理？有什么问题？

SET key value NX EX 30 原子加锁，Lua 脚本比较 value 再删除保证释放安全。问题：主从模式下主节点宕机可能丢锁（可用 RedLock 缓解）。Redisson 看门狗自动续期避免业务未完成锁过期。

### 3. JWT 和 Session 的区别？

Session 有状态，服务端存储会话信息，需要共享 Session。JWT 无状态，Token 中携带用户信息，服务端不存储，天然支持分布式。JWT 缺点：无法主动失效（需要黑名单机制）、Token 体积大。

### 4. 缓存穿透、击穿、雪崩怎么解决？

穿透（查不存在的数据）：布隆过滤器+缓存空值。击穿（热点key过期）：互斥锁+永不过期。雪崩（大量key同时过期）：过期时间加随机值+多级缓存+熔断降级。
