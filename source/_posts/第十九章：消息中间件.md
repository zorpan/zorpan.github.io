## 19.1 消息队列核心概念

```
生产者 → Broker（消息中间件）→ 消费者

核心模型：
- 点对点（Queue）：一条消息只被一个消费者消费
- 发布订阅（Topic）：一条消息被所有订阅者消费
```

**使用场景：**
- **异步处理**：注册后发短信/邮件，不用同步等待
- **系统解耦**：订单服务发消息，库存/支付服务各自消费
- **流量削峰**：秒杀请求先入队，后端按能力消费
- **数据同步**：数据库变更通过 Binlog 同步到 ES/缓存

## 19.2 RocketMQ

```
架构：
Producer → NameServer（注册中心）→ Broker（消息存储）→ Consumer

核心概念：
- Topic：消息主题
- Tag：消息标签，用于过滤
- Queue：分区，一个 Topic 有多个 Queue
- ConsumerGroup：消费者组，组内竞争消费
```

**消息类型：**
```java
// 普通消息
rocketMQTemplate.convertAndSend("topic:order", order);

// 顺序消息（同一 OrderId 的消息发到同一个 Queue）
rocketMQTemplate.syncSendOrderly("topic:order", order, order.getOrderId().toString());

// 延迟消息
Message<Order> message = MessageBuilder.withPayload(order).build();
rocketMQTemplate.syncSend("topic:order", message, 3000, 3);  // 延迟 10 秒

// 事务消息
// 1. 发送半消息（Half Message）
// 2. 执行本地事务
// 3. 根据本地事务结果提交或回滚半消息
// 4. 如果没有确认，Broker 定时回查本地事务状态
```

## 19.3 Kafka

```
架构：
Producer → Kafka Cluster（Broker + ZooKeeper/KRaft）→ Consumer Group

核心概念：
- Topic：消息主题
- Partition：分区，一个 Topic 有多个 Partition
- Replica：副本，Leader + Follower
- Offset：消费位移，记录消费进度
- ConsumerGroup：组内每个消费者消费不同 Partition
```

**Kafka 为什么快？**
1. 顺序写磁盘（append-only）
2. 零拷贝（sendfile）
3. 批量发送和压缩
4. 分区并行

**Kafka 消息可靠性：**
```
Producer：acks=all（所有副本确认）+ retries
Broker：min.insync.replicas=2（最少同步副本数）
Consumer：手动提交 offset（enable.auto.commit=false）
```

## 19.4 RabbitMQ

```
架构：
Producer → Exchange → Binding → Queue → Consumer

Exchange 类型：
- Direct：精确匹配 routing key
- Fanout：广播到所有绑定的 Queue
- Topic：通配符匹配（* 匹配一个词，# 匹配多个词）
- Headers：根据消息头匹配
```

## 19.5 消息可靠性保证

```
生产端：
├── 同步发送 + 重试
├── 事务消息（性能差）
└── 本地消息表（推荐）

Broker：
├── 同步刷盘（不丢消息，慢）
├── 异步刷盘（可能丢少量，快）
└── 多副本同步

消费端：
├── 手动 ACK（处理完再确认）
├── 幂等消费（唯一 ID + 去重表）
└── 死信队列（多次失败转入死信）
```

### 幂等性保证

```java
// 消费端幂等处理
@RocketMQMessageListener(topic = "order-topic", consumerGroup = "order-group")
public class OrderConsumer implements RocketMQListener<Order> {
    @Override
    public void onMessage(Order order) {
        // 1. 查询消息是否已处理（唯一消息ID + 去重表）
        if (messageLogService.isProcessed(order.getMsgId())) {
            return;  // 已处理，跳过
        }
        // 2. 处理业务逻辑
        orderService.process(order);
        // 3. 记录已处理
        messageLogService.markProcessed(order.getMsgId());
    }
}
```

## 19.6 消息积压处理方案

```
问题：消费者消费速度跟不上生产速度

解决方案：
1. 增加消费者数量（需要同步增加 Queue/Partition 数量）
2. 消费者批量消费
3. 跳过非重要消息
4. 临时扩容：将消息转发到更多 Queue，增加消费者
```

## 面试精选

### 1. 为什么要用消息队列？

异步处理（提升响应速度）、系统解耦（服务独立演进）、流量削峰（保护后端系统）。代价：系统复杂度增加、可用性降低、一致性问题。

### 2. RocketMQ、Kafka、RabbitMQ 怎么选？

RocketMQ：阿里开源，事务消息、延迟消息，适合电商/金融。Kafka：高吞吐，适合大数据/日志/流处理。RabbitMQ：AMQP 协议，功能丰富，适合中小规模。

### 3. 怎么保证消息不丢失？

三个环节：生产端（同步发送+重试）、Broker（同步刷盘+多副本）、消费端（手动ACK+幂等消费）。RocketMQ 事务消息或本地消息表保证生产端可靠。

### 4. 怎么保证消息幂等性？

消费端用唯一消息ID+去重表/Redis判断是否已处理。数据库操作用唯一约束保证幂等。乐观锁版本号也可以。

### 5. 消息积压怎么处理？

增加消费者数量（需同步增加分区）、批量消费、跳过非重要消息、临时扩容转发。根本解决：优化消费逻辑、提升消费速度。
