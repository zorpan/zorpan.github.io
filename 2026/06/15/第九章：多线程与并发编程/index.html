9.1 线程基础

9.1.1 进程与线程

  • 进程：操作系统资源分配的基本单位，拥有独立的内存空间
  • 线程：CPU 调度的基本单位，一个进程可以包含多个线程，线程共享进程的内存空间
  • 区别：进程之间内存隔离，线程之间共享堆内存和方法区，但每个线程有自己的程序计数器、虚拟机栈和本地方法栈

9.1.2 创建线程的方式

1. 继承 Thread 类

2. 实现 Runnable 接口

3. 实现 Callable + FutureTask

4. 线程池（推荐方式，后面 9.7 详解）

面试考点： 为什么推荐线程池？因为频繁创建/销毁线程开销大，线程池能复用线程、控制并发数、管理任务队列。

9.1.3 线程的生命周期（六种状态）

状态 说明
NEW 创建但未调用 start()
RUNNABLE 就绪或正在运行（JVM 层面不区分）
BLOCKED 等待获取 synchronized 锁
WAITING 无限期等待（wait、join、park）
TIMED_WAITING 有限期等待（sleep、wait(timeout)）
TERMINATED run() 方法执行完毕或异常退出

9.1.4 线程常用方法对比

方法 是否释放锁 是否抛异常 说明
sleep(n) 否 InterruptedException 暂停执行指定时间（进入 TIMED_WAITING），不释放锁
wait() 是 InterruptedException Object 方法，必须在 synchronized 中调用
join() 否 InterruptedException 等待目标线程执行完毕
yield() 否 否 提示调度器让出 CPU，但不保证生效
interrupt() — — 设置中断标志位，不会中断线程

面试考点：sleep 和 wait 的区别？

  1. sleep 是 Thread 的静态方法，wait 是 Object 的实例方法
  2. sleep 不释放锁，wait 释放锁
  3. sleep 无需在 synchronized 中调用，wait 必须在 synchronized 中调用
  4. sleep 到时间自动恢复，wait 需要 notify/notifyAll 唤醒

9.2.1 synchronized 的三种用法

9.2.2 synchronized 底层原理

  • 同步代码块：编译后在字节码层面生成 monitorenter 和 monitorexit 指令

锁状态 Mark Word 内容 标志位
无锁 HashCode + 分代年龄 01
偏向锁 线程 ID + Epoch + 分代年龄 01
轻量级锁 指向栈中锁记录的指针 00
重量级锁 指向 Monitor 对象的指针 10
GC 标记 空 11

9.2.4 锁升级过程（JDK 6+ 优化）

偏向锁（Biased Locking）

  • 场景：只有一个线程反复进入同步块
  • 原理：第一次获取锁时，将线程 ID 记录到 Mark Word 中，后续同一线程进入时只需比较线程 ID，无需 CAS 操作
  • 开销：几乎零开销

轻量级锁（Lightweight Locking）

  • 场景：多个线程交替进入同步块（无实际竞争）
  • 原理：JVM 在当前线程栈帧中创建锁记录（Lock Record），将 Mark Word 复制到锁记录中，通过 CAS 尝试将 Mark Word 指向锁记录
  • 失败则自旋等待

重量级锁（Heavyweight Locking）

  • 场景：多个线程真正同时竞争锁
  • 原理：未获取锁的线程会被阻塞（挂起），通过操作系统的 Mutex Lock 实现，涉及用户态→内核态切换，开销较大

面试考点：synchronized 锁升级能降级吗？
重量级锁在 GC 时可以降级，但偏向锁和轻量级锁不能主动降级。JDK 15 开始默认禁用偏向锁（JEP 374），因为现代应用中偏向锁的收益很小，反而增加了撤销开销。

9.4 JMM（Java 内存模型）与 happens-before

9.4.1 JMM 抽象结构

JMM 定义了线程之间共享变量的可见性规则：

  • 所有变量存储在主内存
  • 每个线程有自己的工作内存（CPU 缓存的抽象）
  • 线程对变量的操作必须在工作内存中进行，不能直接读写主内存
  • 线程间变量传递必须经过主内存

9.4.2 happens-before 规则

如果操作 A happens-before 操作 B，那么 A 的结果对 B 可见：

  1. 程序顺序规则：同一线程中，前面的操作 happens-before 后面的操作
  2. volatile 变量规则：volatile 写 happens-before 后续的 volatile 读
  3. 监视器锁规则：unlock happens-before 后续的 lock
  4. 线程启动规则：thread.start() happens-before 该线程的每个操作
  5. 线程终止规则：线程中所有操作 happens-before thread.join() 返回
  6. 传递性规则：如果 A hb B，B hb C，则 A hb C
  7. 线程中断规则：interrupt() happens-before 检测到中断
  8. 对象终结规则：构造函数结束 happens-before finalize() 开始

面试考点：JMM 解决了什么问题？
JMM 屏蔽了不同硬件和操作系统的内存访问差异，为 Java 程序员提供了一套统一的并发内存可见性保证。核心问题是：CPU 缓存导致的可见性问题、指令重排导致的有序性问题、以及非原子操作导致的原子性问题。

面试考点：AQS 为什么要用 CLH 队列而不是自旋？
纯自旋会让所有等待线程都消耗 CPU，浪费资源。AQS 用 CLH 变体队列：只有队首的线程（head 的后继节点）才自旋尝试获取锁，其余线程通过 LockSupport.park() 挂起，减少 CPU 空转。唤醒时只 unpark 队首线程，避免惊群效应。

9.7 线程池

9.7.1 为什么用线程池

  • 降低资源消耗：复用线程，减少创建/销毁开销
  • 提高响应速度：任务到达时无需等待线程创建
  • 提高可管理性：统一管理、调优、监控
  • 防止资源耗尽：控制最大并发数

面试要点：为什么不先入队再创建线程？
当核心线程满时，新任务先放入队列等待（而非立即创建新线程），这是设计有意为之——优先让核心线程复用，只有队列满了才会创建非核心线程，减少了线程创建的开销。

面试考点：为什么阿里规约禁止使用 Executors 创建线程池？
因为 FixedThreadPool 和 SingleThreadExecutor 使用无界 LinkedBlockingQueue，任务可以无限堆积导致 OOM；CachedThreadPool 最大线程数为 Integer.MAX_VALUE，可能导致创建大量线程导致 OOM。应该手动 new ThreadPoolExecutor() 并显式指定有界队列和合适的拒绝策略。

9.7.7 线程池参数设定经验

  • CPU 密集型任务：核心线程数 = CPU 核心数 + 1（减少上下文切换）
  • IO 密集型任务：核心线程数 = CPU 核心数 × 2（或根据 IO 等待比例计算）
  • 通用公式：线程数 = CPU 核心数 × (1 + IO 等待时间 / CPU 计算时间)
  • 生产环境建议通过压测确定最优值

9.12 ForkJoin 框架与工作窃取

9.12.1 核心思想

  • 分治：大任务递归拆分为小任务
  • 工作窃取：空闲线程从其他线程的双端队列尾部”偷”任务执行，提高 CPU 利用率

9.12.2 使用方式

面试考点：ForkJoinPool 和普通线程池的区别？

  1. ForkJoinPool 使用工作窃取算法，空闲线程可以偷取其他线程队列中的任务
  2. 普通线程池所有线程从同一个队列取任务，存在竞争
  3. ForkJoinPool 适合递归分治型任务，普通线程池适合独立任务
  4. parallelStream() 底层使用 ForkJoinPool.commonPool()

9.13 ThreadLocal 原理与内存泄漏

9.13.1 核心原理

每个 Thread 内部持有一个 ThreadLocalMap，key 是 ThreadLocal 对象（弱引用），value 是存储的值。

9.13.2 内存泄漏原因

当 ThreadLocal 对象被 GC 回收后（弱引用），Entry 的 key 变为 null，但 value 仍然是强引用，不会被回收。如果线程（尤其是线程池中的线程）一直存活，value 就永远不会释放。

解决方案：用完后必须调用 threadLocal.remove()

9.13.3 典型应用场景

  • 数据库连接（每个线程独立的 Connection）

  • 链路追踪（TraceId 传递）

9.14.1 死锁的四个必要条件

  1. 互斥：资源同一时刻只能被一个线程持有
  2. 持有并等待：线程持有资源的同时等待其他资源
  3. 不可剥夺：已持有的资源不能被强制释放
  4. 循环等待：线程之间形成环形等待链

面试考点：如何避免死锁？

  3. 减少锁的粒度和持有时间
  4. 使用并发工具替代手动加锁（如 ConcurrentHashMap）

面试精选

1. synchronized 和 ReentrantLock 的区别？

synchronized 是 JVM 层面的关键字，自动加锁释放锁，不可中断、非公平；ReentrantLock 是 API 层面的类，需手动加锁释放（try-finally），支持可中断、超时、公平锁、多 Condition。JDK 6 以后 synchronized 做了大量优化（偏向锁、轻量级锁），两者性能差距已很小。优先用 synchronized，需要高级特性时用 ReentrantLock。

2. volatile 能保证线程安全吗？

不能。volatile 只保证可见性和有序性，不保证原子性。例如 volatile int count; count++ 在多线程下仍不安全，因为 count++ 是读-改-写三步操作。线程安全需要原子性保证，应使用 AtomicInteger 或 synchronized。

3. 线程池的执行流程？

提交任务 → 核心线程未满则创建核心线程执行 → 核心线程满则放入任务队列 → 队列满则创建非核心线程执行 → 线程数达到最大值则执行拒绝策略。

4. 为什么不建议用 Executors 创建线程池？

FixedThreadPool 和 SingleThreadExecutor 使用无界 LinkedBlockingQueue，任务可以无限堆积导致 OOM；CachedThreadPool 最大线程数为 Integer.MAX_VALUE，高并发下可能创建大量线程导致 OOM。应手动 new ThreadPoolExecutor 并指定有界队列和拒绝策略。

5. CAS 的 ABA 问题怎么解决？

使用 AtomicStampedReference，每次修改时版本号 +1，CAS 时不仅比较值还比较版本号。或者用 AtomicMarkableReference 加布尔标记。

6. ThreadLocal 内存泄漏的原因和解决？

ThreadLocalMap 的 Entry 的 key 是弱引用，GC 后变 null，但 value 是强引用不会释放。线程池场景下线程长期存活导致 value 泄漏。解决方案：使用后务必调用 remove() 方法。

7. CountDownLatch 和 CyclicBarrier 的区别？

CountDownLatch 是一次性计数器，一个线程等待其他 N 个线程完成；CyclicBarrier 是可复用的屏障，N 个线程互相等待到齐后一起执行。CountDownLatch 计数递减，CyclicBarrier 计数递增。CountDownLatch 不能重置，CyclicBarrier 可以 reset。

8. ConcurrentHashMap JDK 7 和 JDK 8 的区别？

JDK 7 使用 Segment 分段锁（默认 16 个），并发度受限于 Segment 数量。JDK 8 放弃分段锁，使用 Node 数组 + 链表/红黑树，通过 CAS + synchronized（锁粒度到桶级别）实现更高的并发度，且引入红黑树优化 hash 冲突。

9. 如何排查线上死锁？

jstack PID 命令可以自动检测死锁并输出涉及的线程和锁信息。jconsole/VisualVM 连接后点击”检测死锁”也可发现。代码层面预防：固定加锁顺序、tryLock 设置超时、减少锁嵌套。

10. CompletableFuture 和 Future 的区别？

Future.get() 会阻塞，CompletableFuture 支持回调无阻塞；Future 不能链式组合，CompletableFuture 支持 thenApply/thenCompose/thenCombine 等链式调用和 allOf/anyOf 多任务编排；CompletableFuture 支持自定义线程池。
