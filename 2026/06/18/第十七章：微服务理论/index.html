17.4 CAP 理论与 BASE 理论

17.4.1 CAP 定理

分布式系统最多同时满足以下三项中的两项：

  • C（Consistency）一致性：所有节点看到相同的数据
  • A（Availability）可用性：每个请求都能得到响应
  • P（Partition Tolerance）分区容错：网络分区时系统仍能运行

分布式系统必须保证 P（网络分区不可避免），所以只能在 C 和 A 之间选择。

17.4.2 BASE 理论

BASE 是 CAP 的折中方案：

  • BA（Basically Available）基本可用：系统在故障时保证核心功能可用
  • S（Soft State）软状态：允许系统存在中间状态（如数据同步中）
  • E（Eventually Consistent）最终一致性：经过一段时间后，所有节点数据一致

大多数互联网系统选择 AP + BASE：放弃强一致性，保证可用性，通过补偿机制实现最终一致性。

17.5 DDD 与微服务结合实践

面试精选

1. 单体、SOA、微服务的区别？

单体所有功能打包在一起，共享数据库。SOA 通过 ESB 集成粗粒度服务。微服务每个服务独立部署、独立数据库、轻量级通信。微服务是 SOA 的进一步细化，强调去中心化、独立部署、技术栈自由。

2. CAP 理论是什么？为什么只能选两个？

分布式系统最多满足一致性、可用性、分区容错中的两项。网络分区不可避免（必须保证 P），所以只能在 C（一致性）和 A（可用性）之间选择。CP 系统（如 ZooKeeper）保证一致性牺牲可用性，AP 系统（如 Eureka）保证可用性牺牲强一致性。

3. BASE 理论是什么？

BASE 是 CAP 的折中：基本可用（核心功能可用）、软状态（允许中间状态）、最终一致性（一段时间后数据一致）。大多数互联网系统选择 AP + BASE，通过补偿机制实现最终一致性。

4. 微服务怎么拆分？

按业务领域垂直拆分（用户、订单、商品），遵循单一职责和高内聚低耦合。推荐用 DDD 限界上下文指导拆分：每个限界上下文对应一个微服务，内部使用聚合根管理数据一致性。

5. 微服务架构有什么挑战？

服务间通信、分布式事务、服务治理（注册发现、负载均衡、熔断降级）、配置管理、链路追踪、部署运维复杂度。需要引入完整的服务治理框架（Spring Cloud）和 DevOps 工具链。
